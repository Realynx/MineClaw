## Counting convention

**C#** (`tools/Complexity`, Roslyn syntax only, the VS Code Metrics / CA1502 convention): 1 + one for each of
`if` (so each `else if` also adds one), `?:`, `while`, `do`, `for`, `foreach`, `catch`, `&&`, `||`, `??`, `??=`, each
non-default `case` label in a switch statement, each switch-expression arm except a bare discard `_ =>`, and each
`and` / `or` pattern combinator (`x is 1 or 2 or 3` counts 2). These are **not** counted: `else`, `default`, `goto`,
`when`, `is`/`not`, and `?.`/`?[]` (the `--count-conditional-access` flag adds them, for parity with ESLint).

A unit is any method, constructor, destructor, operator, property/indexer/event accessor, expression-bodied
property/indexer, local function, or lambda/anonymous method. File-scoped top-level statements count as one unit. A local
function or lambda is measured on its own and does **not** add to its enclosing member, the same way ESLint
treats nested functions. `--inline-lambdas` folds lambdas into their parent instead, which is the VS Code Metrics
behaviour. Names look like `Type.Member`, `Type.Member.Local`, `Type.Prop.get` and `Type.Member.lambda@L123`.
By default the tool skips `bin/`, `obj/`, `third_party/`, generated files (`*.g.cs`, `*.Designer.cs`,
`<auto-generated>` headers) and test projects (`tests/`, `*.Tests/`).

**TypeScript / JavaScript** (`web/scripts/complexity.mjs`) use ESLint's built-in `complexity` rule (classic variant)
unchanged. The script only wraps the rule so it can report each function's full line span and a descriptive name.
ESLint counts everything listed for C#, minus the pattern combinators, and it also counts **`?.` / `?.()`**,
**default parameter values** and `&&=` / `||=`. A TS function with many optional chains therefore scores higher than
the same C# code would. That is intended: the threshold applies per language, as each ecosystem's own linter measures it.
Each function, arrow, method and class-field initializer is measured on its own. Anonymous functions are named after their binding
site and nearest named owner, for example `Arrow function useMemo() callback in StoryMap` or
`Arrow function def('forEach') callback`.

## Running the tools

```sh
# C# (from the repo root; build once, then the dll runs in ~4 s with no further build)
dotnet build tools/Complexity/Complexity.csproj -m:1
dotnet tools/Complexity/bin/Debug/net10.0/Complexity.dll                      # table, worst first, + per-project rollup
dotnet tools/Complexity/bin/Debug/net10.0/Complexity.dll --format json --out docs/dev/complexity/cs.json
dotnet tools/Complexity/bin/Debug/net10.0/Complexity.dll src/MineClaw.Hive/Story --top 20      # one area
dotnet tools/Complexity/bin/Debug/net10.0/Complexity.dll src/MineClaw.Bot --exclude src/MineClaw.Bot/Blueprints
#   --threshold N (default 10)  --all (every function, not only > N)  --tests (include tests/)
#   --inline-lambdas  --count-conditional-access  --fail-over N (exit 1 if any function > N; otherwise always exit 0)

# TypeScript + JavaScript (needs web/node_modules: `npm ci` in web/, or a junction to the main checkout's)
node web/scripts/complexity.mjs                                   # both languages, tables
node web/scripts/complexity.mjs --lang ts --format json --out docs/dev/complexity/ts.json
node web/scripts/complexity.mjs --lang js --format json --out docs/dev/complexity/js.json
node web/scripts/complexity.mjs --lang ts --only web/apps/web/src/features/story --only 'web/packages/contracts/src/story*'
#   --threshold N  --all  --top N  --exclude <prefix>  --fail-over N
```

The lint gate (`npm run lint`, every `eslint.config.js`) is not changed. The `complexity` rule lives only in the
script.

### Rules for every package (behaviour-preserving)

1. **No behaviour change.** Use extract method/class, guard clauses, tables and polymorphism only. Keep output
   byte-identical for strings, JSON, prompts, tool schemas and wire packets. Before restructuring a function whose output
   is not already pinned by a test, add a golden or equivalence test first.
2. **Public and cross-package surface stays the same.** Don't change signatures that other packages call, because
   the packages are merged independently. Refactor inside the package: add private or internal helpers, or new types in
   files inside your scope. Don't add shared helpers to another package's directory, `Directory.Build.props`, the `.sln`, a
   csproj, or `web/packages/contracts/src/index.ts`.
3. **Partial classes** (`StoryColony`, `MinecraftClient`, `BotAgent`, `ScriptSession`, `Release1122Connection`,
   `FakeServer`, …) each sit inside a single package. Their many files share one member namespace, so make a new helper
   name unique within the type, or put the helper in a nested or new static class.
4. **Hot paths** (pathfinder, physics, packet dispatch, Story picker, viewer per-frame code): add no allocations, LINQ,
   closures or boxing per call. Prefer `static` local functions and `[MethodImpl(AggressiveInlining)]` helpers where they
   help. Run the package's benchmark tests and compare them against a run before the change.
5. **Exceptions**: if a function stays above 10 because splitting it would hurt clarity or performance (a flat
   packet-id switch, a vanilla-mirroring formula), leave a one-line `// complexity: <reason>` comment above it and list it
   in your report. Keep these rare.
6. Run RAM-heavy commands through `heavy.sh` with `dotnet … -m:1`, and stop any server you start. Before merging, run
   `dotnet build MineClaw.sln -m:1` and the package's final test command (below).
